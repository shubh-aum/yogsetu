Database Design · Proposed Schema

YogSetu — Database Schema & Normalization Reference

A relational schema for the platform as it exists today across the public site and all three dashboards (Client, Teacher, Admin) — the signup/profile forms, the job board and applications, direct connection requests, messaging, ratings, wallet credits, and the admin's verification, monetization, content and access-control tools. Designed fresh, not reverse-engineered — normalized to 3NF, with BCNF-clean junction tables for every many-to-many relationship, and zero columns that duplicate a value derivable from other rows.

Every FK below is a real DB-enforced constraint — nothing is left to the application layer to keep consistent Computed, not stored — ratings averages, applicant counts, and wallet balances are query results, never cached columns

A · Design Principles

Two roles — client and teacher — share one users table for authentication and account status, then extend it through a one-to-one table each (clients, teachers). This is class-table inheritance: a client row never carries nullable teacher-only columns like years_experience, and vice versa — the alternative, one wide users table with every role's fields bolted on, is exactly the kind of un-normalized design this schema avoids.

Every place the built dashboards show a list picked from a fixed set — a teacher's expertise tags, their certifications, their online-class locations, a requirement's preferred time slots — got its own child table instead of a comma-joined string in a parent column. A delimited string is the single most common normalization bug in schemas like this one, and it's the first thing this design eliminates.

Deliberately not separate tables

"Connection Logs" (admin)SELECT * FROM connections
"Client & Requirement Logs"SELECT * FROM requirements
Teacher's public ratingnot a column — a query
Wallet balancenot a column — SUM() over wallet_transactions
"2 teachers applied" countCOUNT() over requirement_applications
Each of these looked like it needed its own table when reading the dashboards top to bottom. All five are just filtered views over data that already exists elsewhere — adding a table for any of them would create a second source of truth that could drift from the first.

Four checks, applied to every table above rather than argued for once in the abstract.

1NF — atomic values, no repeating groups

Nothing in this schema stores a delimited list in a single column. Every place the built UI lets someone pick several of something — a teacher's expertise tags, their certifications, their online-class locations, package pricing rows, a requirement's preferred time slots — has its own child table: teacher_expertise, teacher_certifications, teacher_online_locations, teacher_pricing_packages, requirement_availability_slots.

2NF — no partial dependency on a composite key

The two true composite-key tables, teacher_expertise(teacher_user_id, style_id) and subadmin_permissions(subadmin_user_id, module_id), carry no non-key attribute at all besides audit metadata (granted_by, granted_at) that depends on the whole pairing, not on either half alone.

3NF — no transitive dependency

Nothing depends on a non-key column of the same table. requirements.city_id points at cities rather than storing city, state and country as three text columns that would all change together — the classic transitive-dependency smell — and the same pattern covers clients and teachers.

BCNF — every determinant is a candidate key

Every non-trivial functional dependency in this schema is already rooted at a table's primary key, so 3NF and BCNF coincide here — there's no table with two overlapping candidate keys that would force a further split.

Redundancy specifically avoided

Teacher's public rating is never stored pre-blended
It's AVG(ratings.stars WHERE status='published') × 0.7 + teachers.team_rating × 0.3, computed on read. Storing the blended 4.9 as a column would need an update every time any one review changes, is added, or is removed by moderation — a classic update-anomaly risk this design has zero of.
Wallet balances are a ledger, not a mutable counter
wallet_transactions is append-only. A stored balance column would require every credit grant and spend to remember to update it in lockstep — one missed update and the number silently drifts from reality.
Applicant and slot-filled counts are COUNT(), not cached integers
"2 teachers applied", "7 of 12 slots booked" — both come from counting rows in requirement_applications and teacher_weekly_availability at query time.
Geography is one chain, not three repeated text columns
countries → states → cities, referenced by FK from clients, teachers and requirements — a city name is spelled exactly one way, everywhere.

Constraint inventory

what actually stops bad data at the database, not just in application code
UNIQUE(client_user_id, teacher_user_id)connections — one relationship per client/teacher pair, ever
UNIQUE(requirement_id, teacher_user_id)requirement_applications — no duplicate applications
UNIQUE(connection_id)ratings — exactly one review per connection
UNIQUE(teacher_user_id, day_of_week, time_slot)teacher_weekly_availability — one row per slot per teacher
CHECK budget_min ≤ budget_maxrequirements
CHECK stars BETWEEN 1 AND 5ratings
CHECK team_rating BETWEEN 1.0 AND 5.0teachers
CHECK booked_connection_id requires is_availableteacher_weekly_availability — can't book an unavailable slot
ON DELETE CASCADE, everywhere a child row is meaningless without its parente.g. delete a connection → its messages and rating go too
ON DELETE SET NULL, everywhere a reference is informationale.g. delete an admin user → their past cms_content_blocks edits stay, unattributed
